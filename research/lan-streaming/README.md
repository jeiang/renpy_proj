# LAN streaming of a desktop game to a browser (ticket #7)

Question: which stack streams a running desktop game (stock Ren'Py or a new engine) from a LAN host to a browser with low latency and returns input? Compare WebRTC options, headless/offscreen rendering per OS, hardware encode, audio, input mapping; which work with the stock engine unchanged, and what does a custom engine gain by encoding its own frames?

Research date 2026-09-29. Repo metadata (licence, last push, latest release) taken from the GitHub API on that date. Statements not backed by a cited source are tagged **[INFERENCE]**. No latency was measured; latency classes are qualitative and **[INFERENCE]** unless a source is given. Saved raw READMEs/docs in this directory (`*.README.*`, `sunshine_*.md`) are the exact texts quoted below; refetch with the `gh api repos/<r>/readme` / `contents/docs/...` calls (all small, no `.gitignore` needed).

## 2. Headless / offscreen rendering per OS (for stock Ren'Py)

Ren'Py itself needs a real display and GL context to play. Facts from the 8.5.3 source (tag `8.5.3.26051504`, the newest 8.5.3-series tag listed; https://github.com/renpy/renpy/tree/8.5.3.26051504):

- Draw backends tried in order: Windows `gl2, angle2, gles2`; Linux aarch64 `gles2, gl2`; else `gl2, gles2`; then `sw` (software renderer) always as last resort; `RENPY_RENDERER` env var or preference overrides ([`renpy/display/core.py` ~L1095-1130](https://github.com/renpy/renpy/blob/8.5.3.26051504/renpy/display/core.py#L1095)).
- `SDL_VIDEODRIVER=dummy` is set by Ren'Py only for CLI commands that display nothing (`renpy/arguments.py` L350-353: `if not display[command]: setdefault SDL_AUDIODRIVER/SDL_VIDEODRIVER=dummy`). A dummy video driver gives no GL context, so it does not run a real game. Consequence: stock Ren'Py cannot render "offscreen" without a display server; the streamer must supply a display.
- `RENPY_DISABLE_SOUND` exists (env var docs), but audio must stay enabled for streaming.

Per-OS options for giving stock Ren'Py a display without a monitor:

## 3. Details per requirement

- **Hardware encode by OS (Sunshine's table, the widest):** Windows - NVENC, AMF, QuickSync, Media Foundation; Linux - NVENC, VAAPI (AMD/Intel/NVIDIA), Vulkan Video; macOS - VideoToolbox (Apple and Intel); software fallback everywhere. Selkies/Neko/webrtcsink only cover Linux hardware encode well.
- **Audio:** Sunshine captures a virtual/default sink (Steam Streaming Speakers or system default on Windows; PulseAudio on Linux; Audio Tap or BlackHole on macOS). Selkies uses PulseAudio -> Opus (`pcmflux`); Neko uses PulseAudio + GStreamer. Browser requires a user gesture before playing audio **[INFERENCE, general browser autoplay policy]**.
- **Input:** all "unchanged" stacks inject OS-level events into the host session, so the game window must be focused in an interactive session (Sunshine needs `input` group on Linux, Accessibility/Screen Recording style permissions on macOS). Web gamepad and keyboard-lock APIs need HTTPS ([moonlight-web README limitations](https://github.com/MrCreativ3001/moonlight-web-stream/blob/master/README.md)). Ren'Py is mostly click/keyboard; gamepad optional.
- **WebRTC on a LAN:** host candidates usually connect without TURN ("When running on a local network, WebRTC peers usually negotiate connections without any issues" - moonlight-web README). Selkies defaults to WebSocket to avoid TURN/UDP setup and needs one port. Browser needs WebCodecs (secure context) for WebSocket transports.
- **Multi-session:** webrtcsink does not share encoders across consumers; Neko is multi-viewer by design; Sunshine is one active stream per app instance (Apollo docs a multi-instance recipe).
- **Ren'Py workload fit [INFERENCE]:** VN scenes are mostly static with occasional transitions, so damage-aware encoding (skip identical frames, spike bitrate on transitions) helps; stream stacks that capture at fixed fps waste encoder time. High-res video playback in-game is the worst case for any capture-based stack since it is decoded by the engine, re-encoded by the streamer.

## 4. What a custom engine gains by encoding its own frames

(All **[INFERENCE]** unless cited; grounded in the documented capabilities above.)

1. **No capture stage, no virtual display, no window focus.** The frame is already a texture in the engine; it goes straight to an encoder (`appsrc` into `webrtcsink`, or an FFmpeg/vendor encoder into str0m/webrtc-rs). Removes DXGI/ScreenCaptureKit/KMS and the OS permission prompts.
2. **Damage/idle awareness.** Engine knows when nothing changed; it can stop encoding, or request an IDR on scene transitions and adjust bitrate. Capture stacks poll fixed-rate.
3. **Direct input.** Browser events (data channel) map to engine input events; no `uinput`/`SendInput`/CoreGraphics injection, no gamepad driver installs (ViGEmBus/Virtual HID Broker).
4. **Native cross-platform headless.** Renders via wgpu/EGL surfaceless offscreen textures; runs on servers without a desktop session on Linux; on Windows/macOS it still needs a GPU context but not a visible display **[INFERENCE, unverified per OS]**.
5. **Audio without loopback devices.** Engine emits its own mixed PCM, encoded to Opus; no BlackHole/virtual sink.
6. **Costs:** we own signalling, congestion control (webrtcsink gives TWCC, FEC, retransmit for free; str0m/webrtc-rs give primitives only), NAT/TURN policy, HW encode integration per OS, and a web client. RGBA->NV12 conversion and GPU-to-encoder zero-copy are per-API work.
7. **Route (b) (Rust host + Ren'Py Python layer):** works like a custom engine if the Rust host owns the GL/wgpu context and presents the final frame; the Python layer is unaffected. **[INFERENCE]**

## 5. Which work with the stock engine unchanged

- Windows/macOS/Linux hosts: **Sunshine + a Moonlight client (native or Moonlight Web)** is the only researched stack that covers all three desktop OSes with hardware encode and unchanged Ren'Py.
- Linux-only hosts: **Selkies**, **Neko**, **Wolf** work with stock Ren'Py Linux builds in a container/desktop session.
- **webrtcsink** works with stock Ren'Py only with an OS-specific capture pipeline we assemble.

## Adjacent findings

- The `renpy/renpy` repo has no `8.5.3` tag: 8.5.3 builds are tags `8.5.3.26043002 ... 8.5.3.26051504` (`gh api repos/renpy/renpy/tags`). `scripts/run-headless.sh` does not exist at `8.5.3.26051504` (a code search on default branch listed it).
- Ren'Py falls back to its `sw` renderer automatically; under Xvfb that path may quietly run slower than gl2 (relevant to any perf test).
- Moonlight Web v3 is still in pre-release; docs on the default branch may not match v2.10.0 (its README says so).
- Windows 10 host is below Sunshine's listed OS requirement (Windows 11+); Apollo's README lists Windows 10+ (`Apollo README` table).

## Implications for the route decision

- **Route (c) (launcher + stock engine + streaming)** is feasible today on all three host OSes by pairing with Sunshine and Moonlight Web (or native Moonlight); browser latency and installation friction (GPL relay, pairing, macOS permissions, Windows virtual display, Windows 11+) are the costs. Linux-only browser play is cheaper with Selkies.
- Stock Ren'Py cannot render offscreen, so streaming it always means a display server/session (virtual or real) plus capture and OS-level input injection.
- **Routes (a)/(b)** can avoid capture, virtual displays and input injection and can be damage-aware, at the price of owning signalling/congestion control/HW-encode integration. Candidate building blocks: GStreamer `webrtcsink` (least code, best Linux HW encode, weak macOS/Windows encoder tuning), str0m or webrtc-rs (Rust-native, more work).
- Recommendation for the map: keep LAN streaming as a separable **sidecar** requirement. Design the engine so the final frame and audio are available as a texture/PCM stream, letting either route (b) or (a) plug into `appsrc`/str0m later; meanwhile route (c) proves the experience with Sunshine + Moonlight Web.
- Not measured here: actual glass-to-glass latency of any option on this hardware. A follow-up benchmark ticket (Sunshine+MoonlightWeb vs Selkies on a Linux host) is the way to close the latency question.
