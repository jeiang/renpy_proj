# Ren'Py 8.5.3 engine anatomy: Python vs Cython vs native

Ticket: jeiang/renpy_proj#2 (part of #1). Question: which parts of Ren'Py 8.5.3 are pure Python, Cython, or native C; how big is each subsystem; what does it depend on; where can a replacement cut?

## Source and method

- Measured tree: `renpy/renpy` annotated tag `8.5.3.26051504` -> commit `39895c1e017f0b36ffea2447d97eccd69d76ee1c` (latest 8.5.3 tag; tags `8.5.3.26042902` ... `26051504` exist, `renpy/versions.py` on it says `8.5.3 "We Can Go to the Moon"` on branch `fix`; `main` is 8.6.0). I did not verify which of these five tags renpy.org shipped as the final SDK; the briefing names 8.5.3 as latest final. Line refs below are to this tag: `https://github.com/renpy/renpy/blob/8.5.3.26051504/<path>`.
- **pygame_sdl2 is no longer a separate dependency in 8.5.x.** The SDL2 binding lives in-tree as `renpy/pygame/` (Cython, ~8k lines) plus `src/pygame/` (C). It is registered under the old names via a `sys.modules` alias shim so games doing `import pygame_sdl2` still work ([`renpy/pygame/__init__.py`](https://github.com/renpy/renpy/blob/8.5.3.26051504/renpy/pygame/__init__.py) lines ~90-115). The standalone `renpy/pygame_sdl2` repo (tag `renpy-8.5.3.26051504` -> `1c8de534`, last commit 2025-06-02, README says maintained only as Ren'Py's underlay) is an older, larger fork (16.7k code lines: also has `font`, `mixer`, `sprite`) and is *not* what 8.5.3 builds. Cloned only for comparison.
- Re-fetch: `./fetch.sh` (clones into gitignored `src/`). Re-measure: `python3 measure.py > loc-by-subsystem.md` (needs `tokei`; I used `nix shell nixpkgs#tokei`-equivalent, tokei 15.0.0 was already on PATH). Output is deterministic (verified 3 runs). Counts are tokei "code" lines (no blanks/comments) of hand-written files only: generated C from Cython (`tmp/gen`) is not in the tree. `launcher/`, `tutorial/`, `the_question/`, `sphinx/`, `scripts/` are excluded (tokei was nondeterministic on their `.rpy` files).
- Assignment of files to subsystems is by first-match glob rules in `measure.py`; mixed files (e.g. `display/core.py`, `atl.py`, `exports/`) sit wholly in one bucket, so per-subsystem numbers are +/- a few hundred lines.

## Headline

- Runtime engine (excluding dev tooling, Live2D/3D, `renpy/common`): **106k code lines = 58.0k Python (55%), 23.4k Cython (22%), 23.6k C/C++ (22%)**. Add 20.6k lines in `renpy/common` (18.1k Ren'Py script + 1.6k Python), which is engine-shipped standard library (game menu, gui, layered images, accessibility, gallery, ...) written in the game language and executed by the interpreter.
- The C is mostly *vendored third-party or thin glue*: SDL_gfx/rotozoom/PNG/JPEG writers in `src/pygame` (~11k), tinyfiledialogs (~6.8k), libhydrogen (~2.9k), and only ~2.0k of Ren'Py's own C for audio/video (`renpysound_core.c`, `ffmedia.c`). Ren'Py-authored native logic is overwhelmingly Cython, not C.
- The Cython layer is where per-frame math lives (render tree, GL2 model renderer, style engine, text glyph layout, software image ops). Everything else per frame (displayable `render()` calls, layout, screen language evaluation, ATL/transform, interaction loop, audio channel scheduling) is pure Python on one GIL thread.
- The engine's runtime Python dependency set is small: stdlib plus `ecdsa` (save tokens, [`savetoken.py`](https://github.com/renpy/renpy/blob/8.5.3.26051504/renpy/savetoken.py)) and optionally `requests`/`six` in edge paths. Python version pinned at 3.12 (`pyproject.toml`: `requires-python = ">=3.12.8,<3.13"`). Native link deps from [`setup.py`](https://github.com/renpy/renpy/blob/8.5.3.26051504/setup.py): libavformat/avcodec/avutil/swresample/swscale (FFmpeg), harfbuzz, freetype, fribidi, SDL2, SDL2_image, libpng, libjpeg, zlib, assimp (+ Cubism Core only if `CUBISM` set).

## Answers to the question's specific items

- **`renpy/` Python vs Cython vs native:** Python 70.1k, Cython 24.9k, C/C++ 24.3k, Ren'Py script 18.1k over the whole `renpy/`+`src/` tree; runtime subset in the headline above.
- **pygame_sdl2:** vendored into `renpy/pygame` in 8.5 (Cython + C over SDL2); still aliased to the old module names.
- **gl2 model renderer:** Cython (6.7k) over an in-tree GL loader (`uguu`, 2.7k Cython); only GL 2.0-compat / GLES 3.0 contexts; input is the `Render` tree; games can inject GLSL.
- **Text/font shaping:** Python layout (`text.py`) + Cython glyph algorithms + FreeType/HarfBuzz/FriBidi C libraries via Cython (`ftfont.pyx`, `hbfont.pyx`, `bidi.pyx`).
- **Audio/video FFmpeg module:** ~2.0k lines of Ren'Py C (`renpysound_core.c`, `ffmedia.c`) + 1.2k Cython binding/filter, called through ~30 Python functions.
- **Rollback/store:** pure Python (`rollback.py`, `revertable.py`, `python.py`) + `pydict.pyx`/`cslots.pyx` for speed; operates on real Python objects.
- **Save pickling:** pure Python around `pickle` with a custom `Unpickler` ([`compat/pickle.py` L274-300](https://github.com/renpy/renpy/blob/8.5.3.26051504/renpy/compat/pickle.py)); zip container; libhydrogen (C) for secretbox encryption only.

## Adjacent findings (not chased)

- Perf-relevant, for the video/stutter ticket: per-frame Python `interact` loop plus `gc` management in `display/core.py` (`consider_gc`, `gc.collect` at L897/L2202; `config.manage_gc`); the image preload runs in a Python thread (`im.py`) so decode competes for the GIL only while in Python, and native decode inside `pygame.image.load` [INFERENCE: releases GIL not checked].
- Web support already exists as Emscripten-specific branches (`renpy.emscripten` in ~10 files, `audio/webaudio.py`, `webloader.py`); out of scope (WASM) but shows Python-level abstractions for audio/loader are already swappable.
- `PyCode` stores source, not bytecode, so released games still need a compatible Python (3.12 syntax/semantics) to run; `cache/bytecode-312.rpyb` is a per-Python-version cache.

## Implications for the route decision

- **Route (a), full Rust with embedded Python for game code:** must reimplement ~58k Python + ~23k Cython lines of runtime (display core 22k, interpreter/AST 13k, render/GL2 ~11k, text 7k, ...) and still embed CPython for `init python` and pickle-compatible `renpy.ast`/store objects; the reimplemented layer has to expose the same `renpy.*`, `Displayable`, `Render`, `store`, `config`, `style`, and GLSL-shader API to game Python. Highest cost, weakest compat guarantee.
- **Route (b), Rust host keeping Ren'Py's Python layer:** the engine gives natural cuts exactly where the perf problems live: `renpy.display.draw` (GL2 renderer + textures, ~25 methods), the audio/video module (~30 functions, CPU `sws_scale` + RGBA upload is the concrete stutter suspect), the pygame/SDL layer (event/window/surface; wide but mechanical), text rasterization (`FTFont`), and asset loading (`loader.py`). Total replaceable native/Cython surface about 40-50k lines, but the Cython modules `cimport` each other and raw `SDL_Surface*`, so the pygame `Surface` ABI is the coupling to design around. Python (55% of runtime lines) stays untouched, preserving rollback/save/`.rpyc` compatibility for free.
- **Route (c), launcher + stock engine + streaming:** needs no engine cuts; the relevant tap points for streaming are `Draw.draw_screen/screenshot` (video frames), the audio mixer callback (`renpysound`), and `pygame.event` (input). The stock GL2/decode paths keep their CPU video conversion cost.
- Across routes: the `.rpyc` + `PyCode`-as-source design and `renpy/common` (18k lines of Ren'Py script) mean nothing short of an embedded Ren'Py-compatible Python interpreter running Ren'Py's own AST/store classes can run released games; the real choice is which of the Cython/C subsystems above to replace, not whether to keep Python.
